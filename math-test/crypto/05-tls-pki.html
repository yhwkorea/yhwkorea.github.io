현대 암호학 · 프로토콜

TLS 1.3은 알고리즘 하나가 아니다

키 합의·인증서·서명·HKDF·AEAD가 어떤 공격을 막는지 시간 순서로 봅니다.

1. 인증서는 공개키에 이름을 붙인다

X.509 인증서는 subject 이름과 공개키, 유효기간, key usage, 제약을 issuer의 서명으로 묶습니다. 서버가 자기 공개키와 자기 서명을 내미는 것만으로는 신원을 증명할 수 없습니다. 공격자도 자기 키 쌍을 만들 수 있기 때문입니다.

2. 인증 경로 검증

서버 leaf 인증서 ← intermediate CA ← trust anchor
     이름·기간·용도       CA 제약          로컬 trust store

브라우저는 서명만 검사하지 않습니다. 요청한 DNS 이름, 시간, basic constraints, key usage, 정책과 경로를 확인합니다. root가 네트워크에서 왔기 때문에 믿는 것이 아니라 운영체제·브라우저의 trust store에 미리 들어 있기 때문에 출발점이 됩니다.

3. ClientHello

클라이언트는 지원 버전, cipher suite, signature scheme, key share와 난수를 보냅니다. TLS 1.3에서 cipher suite는 주로 AEAD와 hash를 고르며, 서명 방식과 key exchange group은 별도 협상 축입니다.

4. ServerHello와 키 스케줄

서버가 key share를 고르면 양쪽은 (EC)DHE 공유 비밀을 계산합니다. HKDF key schedule은 이 값과 transcript를 결합해 handshake traffic secret을 만듭니다. 이후 handshake 메시지 일부는 이미 암호화됩니다.

5. CertificateVerify

서버는 인증서 공개키에 대응하는 비밀키로 지금까지의 handshake transcript에 서명합니다. 인증서 자체에 찍힌 CA 서명과 CertificateVerify의 서버 서명은 다른 목적입니다.

6. Finished

Finished는 handshake secret에서 만든 키로 전체 transcript를 인증합니다. 공격자가 협상 옵션이나 key share를 바꾸면 양쪽 transcript가 달라져 검증에 실패합니다.

7. Application record

TLS 1.3은 방향별 application traffic key와 sequence에서 nonce를 만들고 AEAD로 record를 보호합니다. record header 일부는 AAD가 됩니다. TLS가 endpoint 내부 악성 코드나 신뢰한 서버의 오용까지 막는 것은 아닙니다.

8. 0-RTT의 별도 위험

재연결 속도를 위해 보내는 0-RTT early data는 replay될 수 있습니다. 서버는 결제·상태 변경처럼 반복되면 위험한 요청을 0-RTT로 허용할지 애플리케이션 수준에서 결정해야 합니다.

9. PQC 전환에서 바뀌는 부품

주로 key establishment의 (EC)DH 자리에 ML-KEM을 단독 또는 하이브리드로 결합하고, 인증서와 CertificateVerify 서명을 PQ 방식으로 바꾸는 작업입니다. 키·서명·인증서가 커지면 handshake fragmentation, MTU, 메모리와 지연까지 다시 측정해야 합니다.
